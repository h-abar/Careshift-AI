# Careshift AI — الفكرة العامة والأدوار

## الفكرة العامة

**Careshift AI** منصة ذكاء سريري وتأميني ثنائية اللغة (عربي RTL / إنجليزي LTR)
تحوّل الرعاية الصحية من نظام يتفاعل بعد وقوع المشكلة إلى نظام **يتنبأ بالخطر،
يتدخل، يوثّق التدخل، ثم يربط النتيجة بالقيمة السريرية والتأمينية**.

المشكلة التي يعالجها: سوء التسليم بين الورديات، تأخر التشخيص، تفويت علامات
التدهور، تصعيدات العناية المركزة، زيادة مدة البقاء، والمطالبات المكلفة أو
المرفوضة. الحلقة المغلقة في المنتج:

```
بيانات المريض → كشف الخطر بالذكاء الاصطناعي → تدخل سريري → إغلاق الحلقة → دليل → قيمة تأمينية
```

المبدأ: *Predict. Intervene. Prove. — تنبّأ. تدخّل. أثبت.*

القصة المركزية في البيانات التجريبية: المريض **P-1042** يتدهور ضمن مسار
**87 → 42 → 18** (حالة DKA)، فيلتقط النظام الانحدار، يُشغّل خطة تدخل،
يوثَّق التنفيذ بأختام زمنية وفاعلين، فتصل جاهزية الأدلة للمطالبة إلى ~96%.

## الأدوار وما يراه / يفعله كل منها

| الدور | الحساب التجريبي | يرى | يفعل |
|---|---|---|---|
| **ممرض/ممرضة** (Nurse) | `s.ahmed` | قائمة المرضى، ملف المريض الكامل (علامات/مختبرات/تاريخ الخطر)، خطة التدخل، مركز الإشعارات، التسليمات الواردة | إعادة تقييم الخطر، تنفيذ خطوات التدخل وتوثيقها، قبول/رفض التسليم الموجّه إليه |
| **ممرضة رئيسية** (Charge Nurse) | `k.mohammed` | كل ما تراه الممرضة + إدارة التسليمات | إنشاء تسليم SBAR، إدارة المراجعة والتوقيع، القبول نيابةً عن الآخرين (manager bypass)، تحديث العلامات الحيوية |
| **طبيب** (Physician) | `a.salem` | المرضى والخطر، خارطة رحلة المريض، التسليمات، الإشعارات (تصله تنبيهات تجاوز العتبة للمرضى المكلف بهم) | توقيع التسليمات، الإشراف السريري على التدخلات |
| **مراجع التأمين** (Insurance) | `m.alotaibi` | المطالبات وتفاصيلها وجاهزية الأدلة — **دون قائمة المرضى أو PHI الخام** (عرض تجميعي فقط) | تغيير حالة المطالبة ضمن دورة قانونية (pending→approved/denied→review)، رفض برموز سبب موحدة (عربي/إنجليزي)، استئناف وإعادة تقديم، رفع مستندات (تحقق بصمة الملف + فحص فيروسي) |
| **مدير مستشفى** (Hospital Admin) | `f.shammari` | لوحة القيادة التجميعية، التقارير، سجل التدقيق | قراءة مؤشرات المنشأة والتوفير، تصدير سجل التدقيق CSV/JSON، مراجعة الصلاحيات والحسابات الخاملة |
| **مدير النظام** (Admin) | `o.khalil` | كل شيء + إدارة المستخدمين + التدقيق | إنشاء/تعليق/فك قفل المستخدمين، إعادة كلمة المرور، «عرض كـ» (انتحال مُدقَّق بشريط واضح)، تصدير التدقيق، مراجعة الوصول |

حساب تجريبي إضافي `r.farouk` (موقوف) لإظهار رفض الدخول المُدقَّق.

## ما لا يراه كل دور (تقليل PHI)

- مراجع التأمين: لا يرى قائمة المرضى ولا الإشعارات المرتبطة بمرضى —
  يحصل على **مجاميع فقط**.
- قوائم اختيار الموظفين (`/api/handoffs` وغيرها): تعرض الهوية والاسم
  والدور والقسم فقط — لا بريد/هاتف/رقم وظيفي.
- الإشعارات المرتبطة بمريض تُسلَّم حصرًا لمن يملك `patients_view`.
- الحساب الموقوف: جلساته تُبطَل فورًا وتُدقَّق محاولات دخوله.

## طبقات الأمان والامتثال (بإيجاز)

- جلسات قاعدة بيانات + JWT بمفتاح قابل للتدوير (`kid` s1/s0).
- RBAC مفروض في الخادم لكل مسار (الإخفاء في الواجهة ليس هو الحماية).
- قفل محاولات الدخول (مطلق لكل اسم+IP، وبوابة CAPTCHA للقفل الواسع) +
  حدود معدل بقاعدة البيانات مع `Retry-After`.
- CSP بنونس، HSTS، حماية CSRF بالأصل، رفع ملفات مفحوص النوع والحجم
  وماسح فيروسي قابل للتوصيل.
- امتثال موجَّه نحو PDPL/NCA ECC: إقرار بيانات تجريبية أول دخول، سياسات
  احتفاظ وتنقية مُدقَّقة، تصدير تدقيق، مراجعة وصول — التفاصيل في
  `docs/compliance.md`.
- قاعدة بيانات PostgreSQL، نشر بـDocker Compose، ومراقبة عبر
  `/api/health` و`/api/ready` و`/api/metrics`.

## ملاحظة

كل البيانات والحسابات **تجريبية محاكاة** — ليست بيانات مرضى حقيقية،
والنظام لا يتخذ قرارات سريرية؛ بل يجعل المعلومة الحرجة مستحيلة الإغفال.
